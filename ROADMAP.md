# EVRT2 — Implementation Roadmap / План реализации

**Author of the standard:** Arthur Valiev
**Last updated:** 2026-07-24 (after first live PC↔Android EVRT2 session)

Этот документ — единственный источник правды о том, что из
спецификации EVRT2 **реально работает**, что реализовано частично,
и в каком порядке делать остальное. Обновляется после каждой фазы.

Правило документа: **никаких приписок**. Строка получает ✅ только
после того, как код прошёл живой тест (реальный телефон ↔ реальный
хост), а не только unit-тесты.

---

## Фаза 0 — Ядро протокола ✅ (завершена, июль 2026)

Что доказано живым тестом (телефон Android ↔ ПК-хост, реальный WiFi):

- [x] Wire-формат: 32-байтный заголовок, magic `EVR2`, все типы пакетов (`evrt2_packet.rs`)
- [x] XOR FEC с coverage-классами `i mod K` + **self-describing length prefix** — найден и закрыт реальный протокольный баг: длина восстановленного пакета невосстановима без префикса (`evrt2_fec.rs`, `evrt2_session.rs`)
- [x] Сборка кадров из пакетов с FEC-восстановлением, мультигрупповые кадры (`evrt2_session.rs::FrameReassembler`)
- [x] Handshake HELLO→ACK, FEEDBACK, GOODBYE, IDR_REQUEST — рабочие хелперы
- [x] Adaptive jitter buffer по формуле спеки (EMA α=0.1, клампы 4–50ms / 2ms+ для 47) — живой на клиенте (`evrt2_jitter.rs`)
- [x] Attention Map из реальных сигналов (motion + focus + surprise; w_A=w_G=w_E=0 честно) (`evrt2_attention.rs`)
- [x] Task-01: visible region из карты внимания, send-order, VISIBLE_REGION флаг (bit 8), jitter-bypass, age-ceiling breach detection (`evrt2_scheduler.rs`)
- [x] Task-02: Capability Registry + калиброванный marginal-utility scheduler, замена `RAYON_THRESHOLD` (`execution_capability.rs`)
- [x] Режимы AR2R47: конфиги + state machine переходов — **реализовано и покрыто тестами, но не управляет живой сессией** (`evrt2_modes.rs`)
- [x] EVRT2-only вход: чекбокс на клиенте → `evrt2_only` в LoginRequest → хост пропускает EVRT1-пайплайн целиком (`host.rs::run_evrt2_only_session`)
- [x] Keepalive-дисциплина: FEEDBACK каждые 3с (UDP) + пустые фреймы 1/с (TCP relay) — оба правила рождены из реальных обрывов
- [x] Периодический keyframe (2с) — лечение «рассыпающейся» картинки при потерях

Известные честные ограничения текущего среза:
- 20 FPS фиксированно, CPU-кодек EVRTCK, без perf-тюнинга → заметная задержка
- Байтовые границы VISIBLE_REGION — оценка по среднему размеру тайла, не точные
- DEGRADE_SIGNAL логируется на хосте, на провод не уходит
- Нет шифрования (AuthTag=0), нет WAN (только LAN-кандидаты), один клиент

## Фаза 1 — Производительность + честный Task-01 (следующая)

Цель: «задержка и ссыпется» → плавный стрим, Task-01 до конца.

| # | Задача | Файлы | Критерий приёмки |
|---|--------|-------|------------------|
| 1.1 | FPS 20→60: точный таймер (1ms), приоритет потока High — перенести те же perf-приёмы, что уже есть в живом EVRT1 (`EVRT perf:` в логе) | `evrt2_experiment.rs` | лог показывает стабильные ~60 отправленных FPS |
| 1.2 | Точные байтовые границы тайлов: `EvrtckEncoder` отдаёт смещения тайлов в потоке → VISIBLE_REGION помечает точный диапазон, а не оценку | `evrtck.rs`, `evrt2_experiment.rs` | границы совпадают с реальными тайлами (unit-тест по wire-формату) |
| 1.3 | DEGRADE_SIGNAL на провод: пакет 0x0D (регион + measured_age), обработчик на клиенте, дискретный индикатор деградации в UI | `evrt2_session.rs`, `evrt2_experiment.rs`, Android UI | при инжекции задержки клиент показывает индикатор в том же кадре |
| 1.4 | IDR_REQUEST от клиента при ошибке декодирования (сейчас тип есть, но клиент его не шлёт) | `evrt2_experiment.rs` | битый кадр → запрос → keyframe приходит < 200ms |
| 1.5 | Замер EVRT Gain: логировать attention-weighted age против uniform baseline — первый живой замер метрики из EVRT2CKMAX.md | `evrt2_experiment.rs` | число в логе за сессию |

## Фаза 2 — Режимы AR2R47 вживую

Цель: `evrt2_modes.rs` перестаёт быть библиотекой и начинает управлять сессией.

| # | Задача | Критерий приёмки |
|---|--------|------------------|
| 2.1 | Motion ratio из AttentionMapBuilder → `ModeSelector::evaluate()` каждый кадр на хосте | статичный экран → AR, видео → 2R (по логу) |
| 2.2 | MODE_SWITCH (0x04) на провод + обработчик на клиенте (перенастройка jitter-профиля и FEC под новый режим) | смена режима без разрыва потока |
| 2.3 | FEC перенастраивается по режиму: AR 6+2, 2R 8+2, 47 — off (сейчас всегда конфиг Mode47) | заголовки пакетов несут правильный mode-байт и FEC-поля |
| 2.4 | Bandwidth-floor правило: < 200KB/s → принудительный AR | искусственное ограничение канала переключает в AR |

## Фаза 3 — APF на проводе

Цель: карта внимания перестаёт быть приватной для хоста — клиент получает приоритеты.

| # | Задача | Критерий приёмки |
|---|--------|------------------|
| 3.1 | APF wire-формат: u4-packed кодирование (1020 байт @ 1080p), передача с keyframe | клиент декодирует карту, размеры сходятся |
| 3.2 | Delta-APF (RLE от предыдущей) для межкадровых обновлений | типичный размер 50–200 байт подтверждён |
| 3.3 | Клиент использует приоритеты: порядок декодирования/отрисовки тайлов по P_i | профилировка показывает focus-тайлы первыми |
| 3.4 | Temporal APF (0x04: priority+max_age+confidence, 3 байта/тайл) — только 2R/47 | wire-тест на упаковку/распаковку |

## Фаза 4 — Безопасность (написать EVRT2_SECURITY.md + реализовать)

Сейчас AuthTag=0 и ENCRYPTED не используется — честно задокументированная дыра.

| # | Задача | Критерий приёмки |
|---|--------|------------------|
| 4.1 | Спека EVRT2_SECURITY.md: вывод ключа сессии из существующего EVRT-токена (он уже ходит в EvrtEndpoints), HMAC для AuthTag, AES-GCM для ENCRYPTED | документ в spec/ |
| 4.2 | AuthTag: усечённый HMAC-SHA256 заголовок+payload, отбрасывание пакетов с неверным тегом | подделанный пакет отбрасывается (тест) |
| 4.3 | ENCRYPTED flag: AES-GCM-256 полезной нагрузки | live-сессия с шифрованием, wireshark не видит плейнтекста |

## Фаза 5 — WAN

Сейчас EVRT2-эксперимент работает только по LAN-кандидатам.

| # | Задача | Критерий приёмки |
|---|--------|------------------|
| 5.1 | STUN через EVRT2-сокет (переиспользовать `netif::discover_public_endpoint` — как в EVRT1) | публичный кандидат в списке |
| 5.2 | Multi-candidate race: HELLO во все кандидаты одновременно, первый ответивший путь выигрывает (SDUDP.md § Path Probing) | телефон на мобильном интернете подключается |
| 5.3 | RELAY_WRAP (0x0C): туннель EVRT2 поверх TCP relay + написать transport/RELAY_TUNNEL.md | сессия за symmetric NAT работает через relay |
| 5.4 | Path switching при деградации >3× RTT | искусственная деградация → переключение без разрыва |

## Фаза 6 — Silicon + слияние с боевым пайплайном

Самая большая фаза — EVRT2 из эксперимента становится продуктом.

| # | Задача | Критерий приёмки |
|---|--------|------------------|
| 6.1 | NVENC/MF как RoiEncoding-провайдер внутри EVRT2-потока (сейчас только CPU EVRTCK) — через Capability Registry, не хардкодом | 47-режим реально silicon-only, 60+ FPS |
| 6.2 | `rebalance()` из ReceiverFeedback2 (Task-02 Phase 4): silicon_ok=false → демоция провайдера | симуляция отказа → переключение за один цикл |
| 6.3 | Codec Race для visible region (First Light): EVRTCK vs silicon одновременно, первый готовый уходит | замер выигрыша по времени первого сигнала |
| 6.4 | Cross-codec splicing: provider_id в слайсе, один кадр из разных кодеков | кадр из silicon+EVRTCK слайсов собирается |
| 6.5 | Jitter-инжекция тест-риг (Task-01 M6): 0–40ms P95, 10 минут, ≥99.9% кадров в потолке | автотест критериев приёмки Task-01 |
| 6.6 | Написать transport/FEEDBACK.md и codec/SILICON_PROBE.md по факту реализации | документы отражают код, не наоборот |

## Порядок и зависимости

```
Фаза 1 (перф + Task-01)  ──┐
                            ├──► Фаза 2 (режимы) ──► Фаза 3 (APF)
Фаза 4 (безопасность) ─────┤         │
Фаза 5 (WAN) ──────────────┘         ▼
                              Фаза 6 (silicon + продукт)
```

Фазы 1, 4, 5 независимы друг от друга и могут идти параллельно.
Фаза 2 опирается на 1 (нельзя оценивать переходы режимов на 20 FPS).
Фаза 6 — финальная сборка, требует всего остального.
